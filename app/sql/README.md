# 購買層クイズ 問題データ（Issue #6）

商品カテゴリTOP5から購買集団の「年代・性別・婚姻状況」を当てるクイズの、問題データを作るSQL。

仕様の正本は [#9 の仕様変更コメント](https://github.com/beuxor/pub-internship2026-hackathon-astra/issues/9#issuecomment-5595387038)。

## ファイル

| ファイル | 用途 |
|---|---|
| `01_create_question_bank.sql` | 問題バンク `TEAM_A_DB.DEVELOPMENT.DAY5_QUIZ_QUESTIONS` を作る。再実行可能 |
| `02_verify_question_bank.sql` | 生成結果の検算7本。期待値をコメントに書いてある |
| `03_queries_for_api.sql` | #11（出題API）と #14（採点API）が使うクエリ |

## 実行方法

Snowsightのワークシート、または接続済みのCoCoから流す。ウェアハウスは `TEAM_A_WH`。

```
01_create_question_bank.sql  → 02_verify_question_bank.sql
```

`01` は `CREATE OR REPLACE TRANSIENT TABLE` なので毎回すべて作り直す。既存の大福帳・顧客表・元表は参照のみで、変更しない。TRANSIENT にしているのは同スキーマのdbt生成表と揃えるため（数秒で再生成できるのでTime Travelは不要）。

**再実行すると `QUESTION_ID` が新しく振られる。** プレイ中に実行すると進行中の問題が引けなくなるので、実行は明示操作のときだけにする。定期タスクは作らない。

## テーブルの列

| 列 | 内容 |

| `ANSWER_AGE_BAND` / `ANSWER_GENDER` / `ANSWER_MARRIAGE` | 正解の3属性 |

| `GENERATED_AT` | 生成時刻 |

## #11 と #14 への境界（重要）

**出題時に返してよいのは `rank` と `categoryPath` だけ。**

`buyers`（購入者数）は集団規模の強いヒントになるので、回答前に返してはいけない。`03_queries_for_api.sql` のQ1・Q2は `TRANSFORM` で `buyers` を構造的に落としてあるので、結果をそのまま返しても漏れない。`SELECT *` で取って手で詰め替えるより安全。

正解3属性と `buyers` は、回答後にQ3で取り直す。クライアントが送ってくる正解や点数は使わない。

`QUESTION_ID` は乱数UUID。属性のハッシュにはしていない。**集団は24通りしかないので、ハッシュだと全列挙で逆引きできてしまう。**

## 設計の理由

### ランキングは購入者数。金額合計ではない

`COUNT(DISTINCT USER_ID_HASH)` を使う。金額 `SUM(TOTAL_PRICE)` だと1顧客が上位カテゴリを独占する。実測では、属性の組み合わせ109集団のうち28集団（10人未満）で、TOP1カテゴリ売上の**100%が1顧客**だった。購入者数なら1顧客は1しか数えられない。

副次的に、TOP5が集団の生活実態を反映するようになった。既婚層にキッズファッション、10代男性に文房具、中年独身男性に惣菜と米が出る。

### 集団の定義は顧客表。購買表ではない

人数は `INT_USERS_ENRICHED` から数える。カテゴリ不明の購買しかない顧客も集団に含める（対象18問で796人が該当）。この人たちはランキングには寄与しないが集団の一員なので、人数から落とすと分母を偽ることになる。

`INT_USERS_ENRICHED` と元表の属性値は完全一致することを確認済み（70,113人で年齢・性別・婚姻の差異0件）。どちらで定義しても同じ結果になるが、#9の決定どおり顧客表を正本にしている。

### カテゴリは元表。大福帳とは結合しない

`SHARED_DB.RAKUTEN_EC_RAW.DELIVERABLE_EC_MALL_PURCHASE` 単独で集計する。理由は2つ。

- 大福帳の `CATEGORY_LEVEL_1` は元表と **437,175明細（29.77%）不一致**（`CATEGORY_LEVEL_4` は不一致0件）
- 大福帳経由だと **226,005明細・約914百万円が欠落**する

元表は `ACCOUNTADMIN` 所有なので参照のみ。

### 出題対象を限定している

1. 年齢が判明（NULL 4,837人を除外）
2. 性別が男性/女性（不明6,324人を除外）
3. 婚姻が既婚/未婚（不明8,615／NULL 2,639／死別2,624を除外）
4. 集団の人数が500人以上
5. TOP5が並び順まで一致する集団は人数最大のものだけ残す

条件1〜3は選択肢を2値に固定するため。これをしないと、正解が「死別」の問題でプレイヤーがどう答えても不正解になる。**死別を未婚へ統合するような値の書き換えはしていない。出題対象から外すだけ。**

条件4はしきい値なしだと `0代女性既婚`（2人）等が出題され、5位に**39カテゴリが同数で並ぶ**（タイブレークが実質カテゴリ名順になる）。500人以上ならタイは最大2件。

条件5は実測で1件該当。`30代女性/未婚`（4,021人）と `40代女性/未婚`（1,490人）のTOP5が並び順まで一致するので、大きい方を残している。しきい値を変えても同じ規則で自動的に効く。

**条件4は「どの集団を出題するか」の限定で、「採点母集団」の限定ではない。** 人数の集計に抽出上限やサンプリングは設けていない。

### カテゴリキーと表示

キーは `CATEGORY_LEVEL_1 + CATEGORY_LEVEL_2`。`CATEGORY_LEVEL_2` が NULL のときは `CATEGORY_LEVEL_1` だけにする（`食品 > (なし)` を作らない）。SQL側で対応済みなので、APIから来た `categoryPath` はそのまま表示してよい。

## 画面に書くべきこと

1. **ランキングは購入者数**。「何人が買ったか」であり「いくら買ったか」ではない
2. **出題対象が限定されている**。「年齢・性別・婚姻が判明し、500人以上いる集団から出題しています。全顧客70,113人のうち50,118人（71.5%）が対象です」。**約3割はどう答えても正解にならない**ので、黙って除外しない
3. **「正解」は元データ上の集団ラベル**であり、購買から個人の属性を断定できるという主張ではない

数字は `03_queries_for_api.sql` の末尾のクエリで実測できる。ハードコードする前に照合すること。

## 既知の限界

- 観測期間は2023-04-01〜2024-03-31の1年分。季節性の影響を分離していない
- `スマートフォン・タブレット > スマートフォン・携帯電話アクセサリー` は18問すべてのTOP5に入る。識別に寄与しない枠
- 元表でカテゴリ購買がある顧客は69,092人、顧客マスタは70,113人。1,021人の差がある
- しきい値500は暫定値。1000人以上にすると14集団（重複除外後13問）になる。変更したら `02_verify_question_bank.sql` の期待値も更新すること
